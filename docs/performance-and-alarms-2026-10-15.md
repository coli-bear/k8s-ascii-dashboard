# 목록 이동 성능과 리소스별 알람 검증

검증일: 2026-10-15 (Asia/Seoul)

## 변경 내용

40ms마다 반복되던 목록 필터링·정렬을 스냅샷/수집 revision/메뉴/필터별로 재사용합니다. 넓은 표의 커서 이동은 전체 행을 다시 포맷하는 대신 선택 표시가 있는 두 줄만 바꿉니다. 수집 결과·필터·폭·탭이 바뀌면 새로 계산합니다. 좁은 카드 표시는 기존 렌더링을 유지합니다.

상세 조회 전용 실행 풀을 두어 모니터링·목록 수집 작업의 대기열과 분리했습니다. 상세 닫기·대상 변경·탭 변경·새로고침 시 이전 요청을 취소하거나 추적에서 분리합니다. 이미 실행 중인 kubectl을 강제 종료하는 변경은 아니며, 오래된 결과는 새 화면에 반영하지 않습니다.

각 리소스 목록의 ALARMS와 상세 Warnings/Errors는 동일한 스냅샷 인덱스를 사용합니다. 추가 API 요청은 행별·커서 이동별로 발생하지 않습니다. Pod UID, ownerReferences, Service selector, Node 할당, Namespace 범위를 사용하고, 반복 Event 발생 횟수는 합산하지 않습니다. 수집 실패나 관계 누락의 의미는 [README](../README.md#리소스별-알람과-목록-이동)를 참고하세요.

## 합성 데이터 측정

macOS, Python 3.13에서 합성 Pod 5,000개로 측정했습니다. 실제 Kubernetes API 지연이나 전체 화면 반응 시간을 측정한 수치는 아닙니다.

| 측정 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 같은 목록 선택 계산 25회 | 약 60.2ms | 약 2.6ms, 첫 계산 후 재사용 |
| 커서 이동을 위한 표 처리 10회 | 전체 렌더링 약 1,636.5ms | 초기 표 생성 후 선택 표시 변경 약 0.013ms |

두 번째 항목의 변경 후 수치는 초기 포맷 비용을 제외합니다. 실제 이동에서도 초기 포맷은 한 번 필요하고 이후 커서 이동에 재사용하는 방식입니다. 터미널 출력과 고정 헤더·요약 계산 비용은 이 미세 측정에 포함하지 않았습니다. 실측 값은 데이터·환경·화면 폭에 따라 달라집니다.

## 회귀 검증

- 기존 테스트를 포함한 전체 205개 unittest 통과.
- macOS Python 3.13.0과 3.14.2에서 각각 실행.
- 유휴 프레임·20회 커서 이동 시 전체 목록 선택/표 포맷 횟수가 증가하지 않는지 검증.
- 이전 상세 요청이 실행 중이어도 새 대상의 요청을 제출하고 이전 결과를 버리는지 검증.
- 알람의 owner chain, Service selector, UID 교체, namespace, 중복 Event/수집 오류, 조회 실패, 캐시 갱신 검증.
- 상세 Warnings/Errors 탭이 추가 네트워크 조회 없이 스냅샷을 표시하는지 검증.
- shell 구문, Python 3.9 문법 파싱, 문서 상대 링크/anchor 검증.

실제 kubeconfig·토큰·Secret을 테스트에 사용하지 않았으며 실제 클러스터의 변경·exec를 실행하지 않았습니다. Ubuntu·Rocky 및 실제 Python 3.9 실행은 미검증입니다. Namespace/Topology의 최초 전체 인벤토리 수집이나 느린 API 응답은 여전히 조회 지연의 영향을 받습니다.
